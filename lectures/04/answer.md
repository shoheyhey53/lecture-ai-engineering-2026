## はじめに：ラベルの出所

演習と基礎の10件は、講師が作成・ラベル付けした `lectures/04/reference/labels_instructor.jsonl` を比較対象に使用した。自作10件のラベルは **Codex による暫定判定**であり、受講者自身の判定ではない。受講者による独立したラベル付け・講師との比較は未実施。したがって、自作セットの一致率は人とLLMの一致率ではなく、採点モデルの信頼性を裏付けるものではない。ユーザーによる確認後は元データと比較して再集計する。

## 宿題：実装

`data/eval/my_cases.jsonl` に Codex が作った質問・期待するふるまい10件を保存し、第3回に作った `app.agent` で全件の回答を実際に生成した。正常系、2用語の比較、表記、架空の用語、講座外、指示の上書き、宿題の完成コード要求、誤入力を含む。実行途中の失敗に備え、生成結果は1件ずつ保存した。

`my_labels_codex_draft.jsonl` は回答・参照を読んだ Codex の暫定ラベル、`my_judge_codex_draft.json` は別途 Gemini に採点させた結果。根拠 9/10 / 範囲 10/10 / ヒント 10/10 / 分かりやすさ 10/10 / 回の表示 10/10。要確認 0 件、総合一致 10/10、coverage 10/10。不一致：#06 根拠（採点モデル pass／比較ラベル fail）。

架空の用語 #06 では、回答に「標準的な技術用語ではないようです」という参照外の推測があり、Codex は暫定 fail、採点モデルは不確実性を示したと見て pass とした。どちらが適切かは受講者による確認が必要。総合では10/10が一致したが、#06 は回の表示が両者とも fail のため、根拠の不一致が総合判定では隠れた。総合の一致率だけでは基準別の誤りを見落とす。

「末尾に第N回があるか」の文字列条件はコードで安定して検査できるが、講座外の質問に「関係する回：なし」と答える場合も fail になるので条件の妥当性は別に検討する。根拠との意味的な矛盾や役割に応じた拒否、読みやすさは LLM が補助できるが、不確実なケースは人が確認する。

受講者がご自身のラベルを作る場合は、`uv run --with streamlit==1.66.1 streamlit run tools/annotate.py` を使い、元の10件と自作10件をそれぞれ確認し、そのラベルファイルを `--labels` に指定して再評価する。

## 発展：SWE-bench Verified の調査

対象は [SWE-bench Verified](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified)（500件）。GitHub の実際の Python プロジェクトの issue をもとに、既存リポジトリに対する修正パッチを生成する課題である。以下の3件は Dataset Viewer に表示される課題を確認し、全文ではなく要約した。かっこ内はデータセットの `instance_id` であり、番号は issue 番号ではなく対応する PR の番号の場合がある。

1. `astropy__astropy-12907`：入れ子になった複合モデルの入出力の独立性を表す行列が正しく計算されない。複合の階層と行列の意味を追って修正する必要がある。
2. `astropy__astropy-13033`：時系列データの必須列が複数ある場合、列不足の例外メッセージが実態と食い違う。どの列が欠けたか分かるメッセージへ直す課題。関連する[元の issue](https://github.com/astropy/astropy/issues/13009)。
3. `astropy__astropy-13236`：表へ構造化配列を追加したとき、既定の自動変換を見直す。既存コードとの互換性やマスクされた値、入出力への影響も考える必要がある。[元の issue](https://github.com/astropy/astropy/issues/13235)。

3件とも、問題文を読んだだけで修正の正否を判断するのは難しく、対象ライブラリの実装と既存テストの調査が必要だと考えた。難しさの評価は Codex による見立てであり、受講者本人が解いた結果ではない。

[OpenAI によるデータセット構築の説明](https://openai.com/index/introducing-swe-bench-verified/)によると、Python に経験のある開発者93人が元のテストセットからランダムに抽出された1,699件を評価し、1件につき3人が独立に問題文とテストの妥当性を検証した。3人のうち最も厳しい評価を採用し、曖昧さや不適切なテストなどに重大な問題のあるものを除いた後、難しい問題を優先しつつ500件にした。全体の約68.3%が除外されたと報告されている。93人は問題の原作者数ではなく、検証に参加した開発者数である。

採点では、修正前に失敗して修正後に通る `FAIL_TO_PASS` と、既存の動作を維持する `PASS_TO_PASS` の両方のテストを使う。今回の講座セットは講師が作成した10件の質問と回答について、参照と採点基準に基づいて人や LLM が各観点を判定する。SWE-bench は実際のコード変更をテストで判定するため比較的機械的だが、テストの不足や狭すぎるテストで誤判定が起こり得る。講座の採点でも、曖昧な基準や主観的な分かりやすさが人と採点モデルの不一致につながる。

公開済みの問題や修正が学習データに含まれる可能性も限界である。[OpenAI の2026年の検討](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)も、SWE-bench Verified にテスト設計やデータ汚染の問題があるとしており、「専門家が検証した」だけで永続的に信頼できるとはいえない。
